== Building and developing Yubico Authenticator
This document describes how to build and package Yubico Authenticator from
source.

NOTE: Yubico Authenticator 6+ uses a new codebase built using the Flutter
framework. The previous Qt codebase can be found in the `legacy` branch.

=== Requirements
You will need the Flutter SDK with enabled desktop support, see:
https://flutter.dev/desktop

Development has been done using the "Install from git" method of installing the
SDK, from the "stable" channel.

The workflows pin the SDK in `.github/workflows/env` (`FLUTTER`). Check out
that tag. The moving `stable` tip can be newer than the pin. The pin is
currently 3.47.8. Enable the desktop embedder for the host you are building:

    flutter config --enable-macos-desktop

=== Dependencies
This project uses dependencies specified in `pubspec.yaml` and
`helper/Cargo.toml`. The corresponding `pubspec.lock` and
`helper/Cargo.lock` files pin the versions used when building the app.
The Rust helper also uses crates from the `yubikey-manager` Git submodule.
Helper builds use `--locked`; when updating Rust dependencies, run
`cargo update --manifest-path helper/Cargo.toml` and commit the updated lockfile.
Desktop helper build-cache keys include the lockfile through `helper/**`.

Rust dependency checks use `cargo-deny` with the policy in
`helper/deny.toml`. Install it with `cargo install cargo-deny --locked`
and run `pre-commit run cargo-deny-helper --all-files` from the repository root.
Install pre-commit first. CI runs it with `pipx run pre-commit`;
`uv tool install pre-commit` also works. The helper `cargo fmt` and Clippy
hooks need the `rustfmt` and `clippy` rustup components
(`rustup component add rustfmt clippy`).
The hook checks Linux, macOS, and Windows on x64 and ARM64 separately to avoid
including dependencies from incompatible platform branches. It runs when helper
manifests, the lockfile, the policy, its check scripts, or the SDK submodule
revision change. The policy follows the SDK's baseline, additionally allows ISC
for `rqrr`, and leaves duplicate dependency versions as warnings.
The Clippy hook also runs when the SDK submodule revision changes to check
API compatibility.

==== Versioning (important for package maintainers!)
We recommend bundling this application with all its dependencies, using the
versions specified in the lock files and the submodule revision pinned by this
repository.

=== Building the Yubico Authenticator Helper
The GUI requires a compiled version of Helper to run, which is built from the
sources in `helper/` in this repository. Install Rust and Cargo and initialize the
https://github.com/Yubico/yubikey-manager/[YubiKey Manager] submodule from the
repository root:

    git submodule update --init --recursive

Alternatively, clone this repository with `git clone --recurse-submodules`.
Install `cargo-about` with
`cargo install cargo-about --version 0.9.2 --locked --features cli`.
Build the helper before running `flutter build` or `flutter run`.

==== Windows

For Windows packaging, also build `ykman-svc` from the submodule:

    cargo build --release --manifest-path yubikey-manager\Cargo.toml -p ykman-svc

The local `resources/win/release-win.ps1` packaging script expects the resulting
`ykman-svc.exe` next to the unpacked Windows build artifact.

The MSI and MSIX packages both install `ykman-svc` as an automatic LocalSystem
service. Before installing either package, uninstall any independently installed
`ykman-svc` (for example, one installed by YubiKey Manager CLI); both packages
use the same Windows service name. Installing a package that contains a service
requires administrator privileges. The MSIX requires Windows 10 version 2004
or later and declares the restricted `packagedServices` and
`localSystemServices` capabilities; publishing it to the Microsoft Store may
require approval for these capabilities.

==== macOS

Install the Rust targets `aarch64-apple-darwin` and `x86_64-apple-darwin`
to build the universal helper.

macOS desktop builds need a full Xcode.app. Command Line Tools are not enough:
`xcodebuild` fails while `xcode-select` points at
`/Library/Developer/CommandLineTools`. Select Xcode:

    sudo xcode-select -s /Applications/Xcode.app/Contents/Developer

Install CocoaPods. `macos/Podfile.lock` records CocoaPods 1.16.2. A newer
CocoaPods rewrites only the `COCOAPODS:` line and leaves the pod checksums
unchanged. Do not commit that version stamp unless the pods themselves change.

`flutter build macos` and `flutter run -d macos` download the macOS engine and
run `pod install`. Running `pod install` yourself, which is required before
opening the Xcode workspace, needs the engine cached first. The CocoaPods
post-install hook looks for `darwin-x64/FlutterMacOS.xcframework` even on
Apple Silicon, and `flutter pub get` does not download it:

    flutter precache --macos
    (cd macos && pod install)

Open `macos/Runner.xcworkspace`, which CocoaPods creates. `flutter pub get`
also generates the Swift package under `macos/Flutter/ephemeral/`.

==== Linux (Debian-based distributions)

    $ sudo apt install libu2f-udev pcscd libpcsclite-dev libudev-dev libdbus-1-dev pkg-config libssl-dev

==== Linux (RPM-based distributions)

    # Tested on Fedora 34
    $ sudo dnf install pcsc-lite-devel systemd-devel dbus-devel pkgconf-pkg-config openssl-devel

When prerequisites are installed you build the helper by running `build-helper.sh`
(or `build-helper.bat` on Windows).

The script reads `helper/target/<triple>/<profile>/authenticator-helper`.
Unset `CARGO_TARGET_DIR` if it is set. Otherwise both `cargo build` invocations
succeed and `lipo` fails because the binaries are not in that directory.

NOTE: You will need to re-run the build script if changes have been made to
Helper's code, or if `flutter clean` has been run.

=== Running the app
Before you can build or run the app using the flutter command you need to build
the helper, as described in the previous section!

To start the app, run:

  flutter run -d <os>

where <os> is "windows", "macos", "linux", or an attached Android device name.
use `flutter devices` to list available devices.

On macOS, an iOS simulator build uses the same command with a simulator name.
Boot the simulator first. Flutter only lists simulators that are already
booted. List the installed runtimes, then boot one by the name `simctl` prints:

    xcrun simctl list devices available
    xcrun simctl boot "iPhone 18 Pro"
    flutter run -d "iPhone 18 Pro"

Xcode 27 has no Simulator.app. Device Hub is
`/Applications/Xcode.app/Contents/Applications/DeviceHub.app`. Focus a booted
simulator with `open "devices://device/open?id=<UDID>"`. The UDID comes from
`xcrun simctl list devices`.

The iPhone layout uses a tab bar. The simulator cannot see a YubiKey. The app
links YubiKit Swift 1.4.0. The deployment target is iOS 16. The desktop helper
is not used. Enable the iOS embedder first with `flutter config --enable-ios`.
The Xcode project is `ios/Runner.xcworkspace`.

==== Running on a physical iPhone

Turn on Developer Mode on the phone: Settings → Privacy & Security →
Developer Mode. Until that is on, `flutter devices` can show the phone as
connected with no developer disk image, and `flutter run` tells you to enable
Developer Mode. Pass that command's identifier to `flutter run -d`.

Each developer keeps a team id and bundle id outside the project. Copy the
example and fill in both values:

    cp ios/Flutter/Local.xcconfig.example ios/Flutter/Local.xcconfig

`Local.xcconfig` is gitignored. `Debug.xcconfig` and `Release.xcconfig` include
it after `Signing.xcconfig`, so the local file overrides the committed default
`com.yubico.yubioath`. The Runner target reads
`$(APP_BUNDLE_IDENTIFIER)` and `$(LOCAL_DEVELOPMENT_TEAM)`. The Team ID is the
10-character id under Xcode → Settings → Accounts. Leave those `$(...)`
references in `project.pbxproj`. Choosing a team in Signing & Capabilities
replaces them with a literal. Put the literal back to the variable instead of
committing a team id.

Sign in before the first device build. The status "Signing for Runner requires
a development team" is not a sign-in button. In the Xcode menu bar, choose
Settings → Accounts, click +, and add an Apple ID. With no certificate, the
build stops at "No valid code signing certificates were found."

A personal team cannot register `com.yubico.yubioath`. Xcode reports that the
identifier is not available, so set `APP_BUNDLE_IDENTIFIER` in
`Local.xcconfig` to one that team can register. The same team cannot provision
NFC Tag Reading or the smart-card entitlement. With either key in
`ios/Runner/Runner.entitlements`, automatic signing fails with "Personal
development teams do not support the NFC Tag Reading capability" and creates
no profile. Leave that file empty for a personal team. Restore
`com.apple.developer.nfc.readersession.formats` (NDEF and TAG) and
`com.apple.security.smartcard` only when a paid team is selected. A paid team
that owns `com.yubico.yubioath` can omit `Local.xcconfig` and use the default.

`Info.plist` still has `NFCReaderUsageDescription`, the ISO 7816 AIDs, and
`UISupportedExternalAccessoryProtocols` set to `com.yubico.ylp`. Those keys do
not grant NFC or USB-C. Without the NFC entitlement,
`NFCReaderSession.readingAvailable` is false on a physical iPhone, and YubiKit
throws `SmartCardConnectionError.unsupported`. That is a missing capability,
not a simulator. Scan says NFC is not included in this install. A Lightning
YubiKey 5Ci still connects through `com.yubico.ylp`. NFC and USB-C smart card
need the paid team.

The first launch is denied until the phone trusts the certificate. On the
iPhone, open Settings → General → VPN & Device Management, select the
developer app, and tap Trust. Before that, launch fails with "its profile has
not been explicitly trusted by the user."

A debug build opened from the home screen, or with
`xcrun devicectl device process launch`, shows the iOS 14 message that debug
apps must be started by Flutter or Xcode. `flutter run -d <udid>` is that
start, but it also needs Local Network permission for the process that runs
Flutter. Without it, install can succeed and the Dart VM connection fails with
`SocketException` errno 65 on port 5353. Grant it in System Settings →
Privacy & Security → Local Network.

A release build opens from the home screen without that session:

    flutter build ios --release
    xcrun devicectl device install app --device <udid> build/ios/iphoneos/Runner.app
    xcrun devicectl device process launch --device <udid> <bundle id>

You can add the `--release` flag to `flutter run` for a desktop release build.

=== Building the app
To build the app without running it, use:

  flutter build <os>

where <os> is "windows", "macos", "linux", or "apk".
Builds of the app will be create under `build/<os>/` for desktop, or
`build/app/` for Android.

=== Running tests
This project uses both unit tests and integration tests.

The unit tests can be run with the command:

  flutter test

These do not require a YubiKey, and are relatively quick to run.

Desktop USB integration tests wait up to five seconds for a YubiKey before each
test, then fail with a device-availability error instead of the usual 30-second wait.
Android and NFC tests retain a 30-second wait to allow manual presentation.
This does not shorten explicit removal, reinsertion, or touch waits within tests.

The integration tests are slower but cover more end-to-end functionality. They
require an attached YubiKey to run, and will make modifications to the data
stored on that YubiKey. This tree does not contain
`integration_test/testdoc.adoc`. Use the runner below, and do not run the
device tests without a YubiKey.

The Python integration-test runner uses `uv` and the native `yubikit` package
from the SDK revision pinned in `integration_test/runner.py`. Keep that pin
aligned with the build workflows. Install `uv` separately (`brew install uv`
on macOS). The runner declares Python >= 3.11 and `uv` downloads that
interpreter; the system Python is not used. The first invocation builds the
Python extension and requires Rust and the helper's native build dependencies:

  uv run --script integration_test/runner.py --help

Device discovery and scripting use `yubikit.device` and `yubikit.scripting`;
the legacy `ykman` Python modules are no longer used.


=== Xcode for external agents
Xcode 26.3 and later can let an agent outside Xcode build and inspect the open
project. See
https://developer.apple.com/documentation/xcode/giving-external-agents-access-to-xcode

In Xcode, choose Settings > Intelligence. Under Model Context Protocol, set
"Allow External Agents to Use Xcode Tools" to Always or "While Xcode is Open".

The bridge is `xcrun mcpbridge`. Apple's examples register it with Claude Code
or Codex (`claude mcp add --transport stdio xcode -- xcrun mcpbridge`, or
`codex mcp add xcode -- xcrun mcpbridge`). Cursor uses a project MCP config
instead, `.cursor/mcp.json`:

[source,json]
----
{
  "mcpServers": {
    "xcode": {
      "command": "xcrun",
      "args": ["mcpbridge"]
    }
  }
}
----

Open `macos/Runner.xcworkspace` in Xcode before the agent calls Xcode tools.
Xcode may prompt once to allow that agent. The Runner scheme prepare step runs
`$FLUTTER_ROOT/packages/flutter_tools/bin/macos_assemble.sh`. `flutter pub get`
writes `FLUTTER_ROOT` into `macos/Flutter/ephemeral/Flutter-Generated.xcconfig`.

A restricted sandbox can fail to launch Xcode and report the app as corrupt
even when `xcodebuild -version` succeeds. Run Xcode, `codesign`, and
`build-helper.sh` outside that sandbox.
